```sql
CREATE TABLE orders (
  id CHAR(36) PRIMARY KEY,   -- a value like '6ccd780c-baba-1026-9564-5b8c656024db'
  ...
);
```

A UUID is a 128-bit identifier designed so that separate servers can each make one without colliding. If order numbers are UUIDs instead of 1, 2, 3, the application can pick the number itself without asking the database for one. You also often hear that using a UUID as the primary key (PK) of an InnoDB table makes INSERTs slower and the table bigger.

> **Summary**
> - InnoDB stores rows sorted by PK. If the PK only ever grows, like 1, 2, 3, each new row goes at the very end.
> - With values that have no order, like UUIDv4, each new row lands somewhere in the middle. Full pages get split in two, and pages end up only 1/2 to 15/16 full. Inserting in order fills them to about 15/16.
> - Every secondary index stores the PK value too. When the PK grows from 8 bytes (`BIGINT`) to 36 bytes (`CHAR(36)`), every secondary index grows with it.
> - If you need UUIDs, store them in `BINARY(16)` and use values that sort by time: `UUID_TO_BIN(uuid, 1)` for MySQL's `UUID()`, or UUIDv7 if the application generates them.
{: .prompt-tip }

## A few words first

| Term | In one line |
| --- | --- |
| Row | One record in a table. Here, one order |
| Primary key (PK) | A unique value given to each row |
| Page | The unit InnoDB moves between disk and memory at once. 16KB by default |
| Clustered index | The structure that keeps whole rows sorted by PK. It is the table data itself |
| Secondary index | A list sorted by some other column. It keeps the PK next to each entry so it can find the row |
| Page split | Splitting a full page in two to make room for a new row |
| Buffer pool | Memory where InnoDB keeps the pages it has read from disk |

## Example tables

I'll use these two tables. They have the same columns and differ only in the PK.

```sql
-- 1) A PK that counts up: 1, 2, 3
CREATE TABLE orders_seq (
  id         BIGINT AUTO_INCREMENT PRIMARY KEY,
  user_id    INT NOT NULL,
  amount     INT NOT NULL,
  created_at DATETIME NOT NULL,
  KEY idx_user_id (user_id),
  KEY idx_created_at (created_at)
) ENGINE=InnoDB;

-- 2) A PK that stores the UUID string as is
CREATE TABLE orders_uuid (
  id         CHAR(36) PRIMARY KEY,   -- a UUIDv4 value generated by the application
  user_id    INT NOT NULL,
  amount     INT NOT NULL,
  created_at DATETIME NOT NULL,
  KEY idx_user_id (user_id),
  KEY idx_created_at (created_at)
) ENGINE=InnoDB;
```

## 1. InnoDB stores rows in PK order

Every InnoDB table has one special index called the clustered index. The manual says it holds the row data and is usually the same thing as the primary key. In other words, the whole table is a single B-tree sorted by PK. The glossary describes a B-tree as a structure that is kept sorted at all times.

So the PK value decides **which page a new row goes into**.

## 2. An AUTO_INCREMENT PK always goes at the end

An `AUTO_INCREMENT` PK gives each new row a number bigger than the last one. The new row always has the highest PK so far, so it always goes into the last page. When the last page fills up, InnoDB opens a new page and keeps going, and the earlier pages aren't touched again.

According to the manual, when records are inserted in sequential order (ascending or descending), pages end up about 15/16 full. InnoDB leaves the remaining 1/16 free on purpose, in case rows get longer later.

## 3. Random UUIDs get squeezed into the middle

RFC 9562 defines UUIDv4 as a UUID generated from truly random or pseudorandom numbers. There's no telling whether a new value will be bigger or smaller than the ones before it, so a new row could belong at the start of the table, in the middle, or at the end. RFC 9562 says such values have "poor database-index locality": values created one after another aren't close to each other in the index, so inserts happen at random locations.

The trouble starts when the page a row belongs in is already full. Picture a shelf where books are kept in number order. A middle section is full, and a new book arrives whose number belongs there. The books have to stay in order, so it can't go into whatever section has space. You move about half the books from that section into a new one to make room, then shelve the new book. That's a page split. The MySQL glossary defines fill factor as the proportion of a page taken up by index data before the page is split.

Right after a split, both sections are about half empty. If the next book happens to have a nearby number, it fills one of those gaps. The numbers are random, so nobody knows when such a book will show up. Half-empty sections pile up all along the shelf. The manual says the same thing: with random inserts, pages are from 1/2 to 15/16 full.

| Insert order | Where the new row goes | How full pages get (per the manual) |
| --- | --- | --- |
| Sequential (`AUTO_INCREMENT`) | Always the end | About 15/16 |
| Random (UUIDv4) | A different spot in the middle each time | 1/2 to 15/16 |

With the same number of rows, emptier pages mean you need more of them. The glossary entry for GUID says the same: because successive values aren't in ascending order, they aren't an efficient primary key for large InnoDB tables.

## 4. Pages missing from the buffer pool come from disk

InnoDB keeps the pages it reads from disk in the buffer pool and serves later reads from memory. The manual describes the buffer pool as an area in main memory where InnoDB caches table and index data as it is accessed. To insert a row, the page it belongs in has to be in the buffer pool.

Think of the buffer pool as a desk and the disk as a storage room down the hall. With sequential inserts, only the last section is ever needed, so it stays on the desk. With random inserts, one row needs a section near the front and the next one a section in the middle. Once the table is bigger than the buffer pool, the section you need is often not on the desk, and each time it has to be fetched from the storage room.

As section 3 showed, a random PK also makes the table bigger because pages are less full. A bigger table plus scattered insert spots makes it even harder to keep everything in the buffer pool. MySQL reports how many reads couldn't be served from the buffer pool and had to go to disk in the `Innodb_buffer_pool_reads` status variable. If INSERTs slowed down after switching to a UUID PK, check whether this number went up too.

RFC 9562 notes that the real-world difference between time-ordered values and random inserts can be one order of magnitude or more.

## 5. The PK rides along in every secondary index

A secondary index is a list sorted by a column other than the PK. In the example tables, `idx_user_id` is sorted by `user_id`. The manual says each record in a secondary index contains the PK columns for that row. InnoDB finds the entry by `user_id`, then uses the PK stored next to it to look up the row in the clustered index. With several secondary indexes, the PK value is stored that many more times.

The manual says it directly: if the primary key is long, the secondary indexes use more space, so a short primary key is better.

Here's the size of a single PK value:

| PK type | Size of one value | Source |
| --- | --- | --- |
| `BIGINT` | 8 bytes | Numeric type storage table |
| `BINARY(16)` | 16 bytes | `BINARY(M)` takes M bytes |
| `CHAR(36)` (utf8mb4) | 36 bytes | COMPACT-family row formats reserve at least N bytes for `CHAR(N)`. A UUID string is only hex digits and hyphens, so each character is 1 byte |

With two secondary indexes and a million rows, like the example tables, just multiplying out the PK values in the secondary indexes shows the gap. This is plain arithmetic that leaves out record headers and free space in pages.

| PK type | Calculation | PK values in two secondary indexes |
| --- | --- | --- |
| `BIGINT` | 8 bytes × 1 million × 2 | 16 million bytes |
| `BINARY(16)` | 16 bytes × 1 million × 2 | 32 million bytes |
| `CHAR(36)` | 36 bytes × 1 million × 2 | 72 million bytes |

Secondary indexes are indexes too, so everything in sections 3 and 4 applies to them. Bigger records mean fewer records per page, and bigger indexes are harder to keep in the buffer pool.

## 6. Why MySQL's UUID() is out of order as is

MySQL has a `UUID()` function. According to the manual, it returns an RFC 4122 **version 1** UUID as a string shaped like `aaaaaaaa-bbbb-cccc-dddd-eeeeeeeeeeee`. Version 1 UUIDs are built from a timestamp. The first three groups are the low, middle, and high parts of that timestamp.

Think of a clock. Say you write 3:05:10 backwards, seconds first, as `10-05-03`. If you sort a pile of these notes character by character, they won't come out in time order.

| Actual time | Note written as seconds-minutes-hours | Position after sorting |
| --- | --- | --- |
| 3:01:20 | `20-01-03` | 2nd |
| 3:05:10 | `10-05-03` | 1st |

3:05:10 is the later time, yet it sorts first. `UUID()` works the same way: the fastest-changing part (time-low) comes first, so the sorted order of the strings doesn't match the order they were created in.

`UUID_TO_BIN(uuid, swap_flag)` fixes this. It converts a UUID string to a 16-byte binary value. With `swap_flag` set to 1, it swaps the first group (time-low) and the third group (time-high). That's the same as rewriting the seconds-minutes-hours notes as hours-minutes-seconds. The manual explains that this moves the more rapidly varying part to the right and can improve indexing efficiency.

```sql
SET @uuid = '6ccd780c-baba-1026-9564-5b8c656024db';

SELECT HEX(UUID_TO_BIN(@uuid, 0));  -- 6CCD780CBABA102695645B8C656024DB
SELECT HEX(UUID_TO_BIN(@uuid, 1));  -- 1026BABA6CCD780C95645B8C656024DB
```

This example is from the manual. `6CCD780C` and `1026` trade places, and `BABA` in the middle stays put.

In a table, it looks like this. Use the same `swap_flag` when writing and reading, or you won't get the original string back.

```sql
CREATE TABLE orders_bin (
  id         BINARY(16) PRIMARY KEY,
  user_id    INT NOT NULL,
  amount     INT NOT NULL,
  created_at DATETIME NOT NULL,
  KEY idx_user_id (user_id),
  KEY idx_created_at (created_at)
) ENGINE=InnoDB;

-- Writing: move the time part to the front and store 16 bytes
INSERT INTO orders_bin (id, user_id, amount, created_at)
VALUES (UUID_TO_BIN(UUID(), 1), 42, 15000, NOW());

-- Reading: use the same swap_flag to get the original string back
SELECT BIN_TO_UUID(id, 1) AS id, user_id, amount FROM orders_bin;
```

> The manual says time-part swapping assumes **version 1** values like the ones `UUID()` generates, and gives no benefit for values that don't follow the version 1 format. Don't use `swap_flag` on UUIDv4 or UUIDv7 values from your application.
{: .prompt-warning }

## 7. UUIDv7 comes from the application

RFC 9562 defines a new UUIDv7. It puts a Unix timestamp in milliseconds in the first 48 bits and fills the rest, apart from the version and variant bits, with random bits. Since the time comes first, values made later are generally larger. RFC 9562 explains that time-ordered UUIDs get better index locality because new values sit near each other in the index. Values made within the same millisecond have random trailing bits, so their order can be mixed. The mixing stays inside that one millisecond.

MySQL 8.4 has no function that generates UUIDv7. Among the UUID functions in the manual, the only ones that create values are `UUID()`, which returns version 1, and `UUID_SHORT()`, which returns a 64-bit integer that isn't an RFC UUID. There's no UUIDv4 function either. So UUIDv7 values are generated in the application and stored in `BINARY(16)`.

Applying `swap_flag` to a UUIDv7 breaks the order. The third group holds the version number and random bits, so moving it to the front makes a random value the first thing the sort looks at.

## 8. Comparing the options

| Option | PK value size | Where new rows go | Upside | Watch out for |
| --- | --- | --- | --- | --- |
| UUIDv4 in `CHAR(36)` (example table 2) | 36 bytes | A random spot each time | Easy for people to read | The largest, with frequent page splits and disk reads |
| `BIGINT AUTO_INCREMENT` | 8 bytes | Always the end | The smallest, and rows pile up in order | The database assigns the number. Exposed as is, it reveals the 1, 2, 3 sequence |
| UUIDv4 in `BINARY(16)` | 16 bytes | A random spot each time | Less than half the size of `CHAR(36)` | The ordering problem stays |
| `BINARY(16)` + `UUID_TO_BIN(UUID(), 1)` | 16 bytes | Close to time order | Works with built-in MySQL functions only | Version 1 only. Reads need `BIN_TO_UUID(id, 1)` |
| UUIDv7 in `BINARY(16)` | 16 bytes | Close to time order. Mixed only within the same millisecond | A standard format, time-ordered no matter where in the app it's made | MySQL has no function for it, so the application generates it. Don't use `swap_flag` |
| `BIGINT` internal PK plus a separate public UUID column | 8-byte PK | The PK always goes at the end | Secondary indexes only carry the 8-byte PK | The UUID column needs one more `UNIQUE` index. With UUIDv4 values, that one index still has the section 3 problem |

The last option looks like this:

```sql
CREATE TABLE orders (
  id         BIGINT AUTO_INCREMENT PRIMARY KEY,  -- number used only inside the table
  public_id  BINARY(16) NOT NULL,                -- number shown in URLs and APIs
  user_id    INT NOT NULL,
  amount     INT NOT NULL,
  created_at DATETIME NOT NULL,
  UNIQUE KEY uk_public_id (public_id),
  KEY idx_user_id (user_id),
  KEY idx_created_at (created_at)
) ENGINE=InnoDB;
```

To look up a row by its public number, InnoDB finds the `id` in `uk_public_id`, then reads the row from the clustered index.

## Wrap-up

- InnoDB stores rows in PK order. If the PK always grows, rows go at the end. If it has no order, rows get squeezed into the middle.
- Squeezing rows into the middle splits full pages and leaves half-empty ones behind. More pages are harder to fit in the buffer pool, so disk reads go up.
- The PK value is stored again in every secondary index. A big PK makes all of them bigger.

If a table with a UUID PK is slow, check these in order:

1. If the PK type is `CHAR(36)` or `VARCHAR(36)`, see whether you can switch to `BINARY(16)`.
2. Check where the UUIDs come from. For MySQL's `UUID()`, use `UUID_TO_BIN(uuid, 1)`. If the application makes them, see whether it can use UUIDv7 instead of UUIDv4.
3. Count the secondary indexes. The more there are, the more the PK size matters.
4. Ask whether the UUID really has to be the PK. If you only need a number to show outside, keep a `BIGINT AUTO_INCREMENT` PK inside and add a separate UUID column.
